秒杀场景下 `库存 > 0` 的检查和扣减如果不是原子的，就会超卖。下面是三种我实际试过的方案。

### 方案一：数据库行锁

```sql
UPDATE product SET stock = stock - 1 WHERE id = ? AND stock > 0;
```

看受影响行数，等于 0 就是没抢到。

- 优点：最简单，不用引入中间件
- 缺点：热点行锁竞争，QPS 上不去；事务里还有别的写操作时锁持有时间更长

### 方案二：Redis 预扣 + 异步落库

先用 `DECR` 在 Redis 里扣，扣到负数就回补并拒绝，然后把成功的请求丢进消息队列慢慢写库。

- 优点：扛得住高并发
- 缺点：要处理"Redis 扣了但落库失败"，必须有对账和补偿；超时未支付要还库存

### 方案三：乐观锁

给商品表加 `version` 字段，`UPDATE ... WHERE version = ?`，失败就重试。

- 优点：不加锁，读多写少时表现好
- 缺点：冲突多的时候重试成本高，重试次数要有上限

### 我最后怎么选的

方案二。因为秒杀流量是脉冲式的，数据库撑不住峰值，而 Redis 本来就是链路里的组件。
代价是写了一套对账任务——这部分没做完，是项目的已知缺陷。
